# RK3588 板端摄像头检测与编码链路延时测试报告

报告整理日期：2026-10-21。

本报告整理此前已经完成的三轮实验，并于报告整理时从板端重新读取原始 CSV 复核；本次整理没有重新运行性能测试。板端系统日期曾出现回拨，CSV 文件显示的设备日期为 2026-07-20，不能据此认定真实实验日历日期。延时计算使用单调时钟，不依赖该日历时间。

## 1. 测试目的与结论

本次测试测量 Orange Pi 5 Pro 上“摄像头帧进入用户态后，经目标检测、画框和 H.264 编码，直到取得完整编码包”的逐帧延时，补充此前只有端到端吞吐率（FPS）的性能评价。

三轮各处理 1000 帧，分别排除前 100 帧预热，共获得 2700 个有效统计样本。主要结果如下，单位均为 ms。

| 测量范围 | 样本数 | 均值 | P50 | P95 | P99 | 最大值 |
|---|---:|---:|---:|---:|---:|---:|
| DQBUF 成功后 → MPP 完整编码包取得后 | 2700 | 32.38 | 29.71 | 46.64 | 61.43 | 149.09 |
| V4L2 驱动帧时间戳 → MPP 完整编码包取得后 | 2700 | 66.41 | 64.08 | 81.55 | 98.79 | 182.23 |

前者是本实验约定的正式软件链路口径，后者是基于驱动时间戳的补充口径。两者起点不同，必须同时写明起止点，不能笼统写成“端到端延时为 29 ms”或“端到端延时为 64 ms”。以上均不包含网络传输、接收端解码及屏幕显示，也不是从光学曝光事件开始测得的整机延时。

## 2. 测试链路及起止点

本测试采用逐帧时间戳差值法：对同一帧，在 `VIDIOC_DQBUF` 成功返回后记录起始时间，在同步编码函数 `process_frame()` 取得该帧完整编码包并成功返回后记录结束时间，两者均使用 `CLOCK_MONOTONIC`，相减得到该帧的软件链路延时。该延时覆盖采集后准备、排队、预处理、推理、后处理、画框及编码全过程，不包含网络传输和接收端显示。同时以驱动提供的单调时钟帧时间戳替代起始时间，补充计算“驱动帧时间戳至编码完成”的延时，并在排除预热帧后统计均值及 P50/P95/P99。

### 2.1 实际处理链路

本次启用 `mpp-only`，但该模式仍执行目标检测和画框；名称表示输出到 MPP 编码阶段，不启用 RTMP，也不写 AVI。

```text
USB 摄像头：640×480、YUYV、30 FPS
    ↓ V4L2 采集：MMAP 分配缓冲，VIDIOC_EXPBUF 导出 DMA-BUF fd
VIDIOC_DQBUF 成功返回                         ← 正式起点 t_dqbuf
    ↓ 采集后准备：RGA YUYV→RGB，OpenCV RGB→BGR，构造 Mat/帧引用
读队列 → 聚合线程派发 → 推理线程池等待
    ↓ 工作线程处理（共 6 个 worker）
    ├─ 相机 DMA-BUF → RGA YUYV→RGB、resize 至模型输入尺寸
    ├─ RKNN fd 输入、NPU 执行、copy 模式取输出
    └─ NEON 后处理、检测结果还原、在 Mat 上画框
结果按帧号保序输出 → 写队列 → 唯一写线程
    ↓ Mat 数据复制到编码前中间缓冲，RGA 转 NV12
process_frame()：NV12 拷贝到 MPP 输入缓冲 → 提交 → 阻塞取编码包
process_frame() 成功返回                       ← 终点 t_mpp_complete
```

采集使用的是“V4L2 MMAP 缓冲导出 DMA-BUF”方式，而非将 `VIDIOC_REQBUFS` 的 memory 参数设置为 `V4L2_MEMORY_DMABUF`。本次链路保留 Mat 供画框和 MPP copy 路径使用，因此不能称为全链路零拷贝；也没有开启 `--camera-zero-copy-mpp`。

### 2.2 正式延时定义

```text
L_software = (t_mpp_complete - t_dqbuf) / 1,000,000
```

两个时间戳均为纳秒，结果单位为 ms。

`t_dqbuf` 在采集函数确认 `VIDIOC_DQBUF` 成功后立即读取 `CLOCK_MONOTONIC`；`t_mpp_complete` 在写线程的 `process_frame()` 返回后读取。终点包含少量函数返回与软件清理开销，不是硬件中断时间戳。

MPP 设置为阻塞取包（`MPP_SET_OUTPUT_TIMEOUT = MPP_POLL_BLOCK`）。编码调用提交输入帧后调用 `encode_get_packet()`；遇到分片包时继续取包，直到 EOI（该帧编码结束）。本次单写线程同步逐帧提交，成功返回可用作该帧完整编码包已取得的完成点。MPP copy 模式下，输入数据复制也计入该调用耗时。

### 2.3 驱动时间戳补充口径

采集时同时读取 DQBUF 返回的 `buf.timestamp`。当驱动标记其使用单调时钟时，计算：

```text
L_driver = (t_mpp_complete - t_v4l2) / 1,000,000
L_upstream = (t_dqbuf - t_v4l2) / 1,000,000
```

`buf.timestamp` 是驱动提供的帧时间戳，不是应用调用 QBUF 的时刻。现有记录仅保存其时间值及“是否标记为单调时钟”，没有保存完整的 `TSTAMP_SRC_EOF/SOE` 源标志，也没有核验本机 UVC 驱动的具体打点实现。因此不能将它直接称为曝光开始时间。

`L_upstream` 是驱动时间戳至用户态 DQBUF 的实际时间差。它可能包含驱动时间戳对应事件后的帧传输、组帧、缓冲排队及线程调度等，现有数据不能进一步划分。不能将全部约 34 ms 都归因于驱动队列等待，也不能仅因接近 30 FPS 的一帧周期就判定其全部为成帧时间。

## 4. 测试方法与统计规则

### 4.1 埋点及数据记录

每帧携带 `FrameLatencyTrace`，在采集、入读队列、聚合派发、worker 开始/结束、结果保序、取写队列、编码前 RGA 开始/结束、MPP 调用前/后记录时间戳。所有软件埋点均使用 `CLOCK_MONOTONIC`。

唯一写线程在该帧编码完成后追加内存记录，所有线程结束后一次性写 CSV，并打印汇总结果。该设计避免为延时埋点新增逐帧打印和逐帧文件写入；原程序仍有性能监控及正常初始化日志。

### 4.2 预热与样本选择

每轮采集并处理帧编号 0～999。编号 0～99 是预热帧，仍写入 CSV，但不进入正式延时统计；编号 100～999 中编码成功、时间有效的记录为统计样本。三轮统计样本合并为 2700 帧，而不是对三轮 P95 等指标简单求平均。

历史命令同时带有 `--warmup 50` 与 `--latency-warmup 100`。代码核实：前者仅用于 `rknn-only` 模式，本次 `mpp-only` 不额外执行这 50 次预热；本报告真正采用的延时预热数量为每轮前 100 帧。

### 4.3 统计量及完整性检查

本报告从 CSV 的原始纳秒时间戳重新计算区间，统一采用与程序一致的线性插值分位数：将 n 个样本升序排列，计算位置 `p×(n−1)`，对相邻两个值线性插值。表格保留两位小数。此前聊天中的三轮合并统计采用了不同的取整分位数方法，个别末位略有差异；以本报告统一复算结果为准。

每轮检查 CSV 总条数、有效样本数、编码成功标志、应用帧号唯一性与覆盖范围、埋点时间顺序。采集超时和 RGA Oops 以原运行时的终端输出及测试后内核检查为依据；本次整理时历史 `/tmp/latency_run*.log` 已不在板端，不能从当前内核日志重新证明历史启动周期的状态。

“无缺失帧”在本报告中指应用编号 0～999 均有唯一编码记录。CSV 未记录 V4L2 `buf.sequence`，因此不能由此证明相机或驱动没有丢失任何源帧。

### 4.4 同配置复现命令

以下命令每次创建新的结果目录，连续启动三个独立进程。为复现正式测试中的工程 RGA 库，显式清除可能覆盖 RUNPATH 的 `LD_LIBRARY_PATH`；运行前应确保工程运行库齐全，实际 RGA 版本为 `1.9.1_[4]`。命令用于复现，本次整理报告时未执行。

不带注释版本：

```bash

mkdir -p ../debug_records
latency_dir=$(mktemp -d ../debug_records/latency_repeat_XXXXXX)
for run in 1 2 3; do
  env -u LD_LIBRARY_PATH V4L2_BUFFER_COUNT=8 timeout 180s ./app \
    --mode mpp-only --input camera --input-backend dmabuf \
    --camera-id 0 --camera-width 640 --camera-height 480 \
    --camera-fps 30 --camera-format YUYV \
    --threads 6 --loops 1000 --warmup 50 \
    --rknn-input-mode fd --rknn-output-mode copy --mpp-input-mode copy \
    --preprocess-backend rga --postprocess neon \
    --box-threshold 0.5 --nms-threshold 0.5 \
    --model-path ../model/yolov5s_relu_INT8_Normal.rknn --skip-sigmoid \
    --latency-warmup 100 --latency-csv "$latency_dir/run${run}.csv" \
    --latency-summary > "$latency_dir/run${run}.log" 2>&1 || break
done
printf '%s\n' "$latency_dir"
```

## 6. 结论与适用范围

在 640×480 YUYV@30 FPS 摄像头、8 个 V4L2 buffer、6 个推理线程、YOLOv5s ReLU INT8、RKNN fd 输入、NEON 后处理及 MPP copy 编码配置下，板端软件处理至编码包完成的延时为 P50 29.71 ms、P95 46.64 ms、P99 61.43 ms，最大 149.09 ms。以驱动帧时间戳为起点时，P50 为 64.08 ms、P95 为 81.55 ms、P99 为 98.79 ms。

三轮测试验证了该配置可连续完成每轮 1000 个应用帧的检测与编码，未观察到编码失败及新增 RGA Oops。但测试规模仅为三轮、3000 个应用帧，不能替代长时间稳定性验证，也不构成严格的最坏情况延时保证。不能据此宣称网络播放延时低于 100 ms，或证明所有相机源帧都无丢失。

本报告结果只适用于上述测试配置与代码版本。改变模型、输入分辨率、线程数、MPP copy/fd 模式、缓冲策略或视频输出方式后，应重新测量，不能直接混用本报告数据。
