> SiLU 的延迟分布很宽 (41-80ms)，说明 NPU 在处理 Sigmoid+Mul 时存在不可预测的流水线停顿。

## 5. 算子融合

| | SiLU | ReLU |
|---|---|---|
| 激活函数 | x × sigmoid(x) | max(0, x) |
| ONNX 算子数 | Sigmoid 60 + Mul 75 = 135 | Relu 57 |
| NPU 融合 | ❌ 无法与 Conv 融合 | ✅ ConvRelu (50) + ConvReluAdd (7) |

```
SiLU:  Conv → 写DDR → 读DDR → Sigmoid → 写DDR → 读DDR → Mul → 写DDR
ReLU:  Conv → ReLU(就地) → 写DDR (一次)
```

## 6. 深度分析

### 6.1 为什么 ReLU 比 SiLU 快这么多？

核心原因在**内存带宽**, 不在计算量。

```
SiLU 每层的数据流:
  Conv 计算 (NPU内部) → 结果 28KB, 写 DDR → 下一算子读 DDR, 28KB → Sigmoid → 写 DDR, 28KB
  → 读 DDR, 28KB → Mul → 写 DDR, 28KB → 下一层读 DDR
  每层 DDR 读写总量: 28KB × 6 = 168KB (Conv→out, Sigmoid in/out, Mul in/out, next in)

ReLU 每层的数据流:
  Conv 计算 (NPU内部) → ReLU (NPU内部, 就地操作) → 结果 28KB, 写 DDR → 下一层读 DDR
  每层 DDR 读写总量: 28KB × 2 = 56KB (ConvReLU→out, next in)
```

YOLOv5s 有约 60 个卷积层, 每张 640×640 图片推理时:
- SiLU: 60 层 × 168KB = 约 **10 GB** DDR 流量
- ReLU: 60 层 ×  56KB = 约 **3.4 GB** DDR 流量

RK3588 的 DDR 带宽约 25-30 GB/s, 但 NPU 和 CPU/GPU/RGA 共享。SiLU 多出的 6.6GB 流量在 NPU 繁忙时会排队等待——这解释了为什么 SiLU 的延迟波动那么大 (41-80ms), 而 ReLU 几乎不变 (17.4-18.9ms)。

### 6.2 P50/P95 的巨大差距说明了什么？

| | SiLU | ReLU |
|---|---|---|
| P50 | 45.2 ms | 17.8 ms |
| P95 | 64.6 ms | 18.0 ms |
| P95/P50 比值 | **1.43x** | **1.01x** |
| 尾延迟 (P99-P50) | **30.4 ms** | **0.2 ms** |

P95/P50 比值反映了系统的**可预测性**:

- **SiLU 的 P95/P50 = 1.43**: 意味着 5% 的推理帧会比典型帧慢 43%。在实时视频分析场景, 30fps 的目标帧间隔是 33ms——SiLU 连 P50 都超出了这个预算 (45ms), P95 更是达到 65ms, 几乎占了两帧的时间。这会导致**不可预测的帧丢失**。

- **ReLU 的 P95/P50 = 1.01**: 几乎完美的确定性延迟。每一帧都在 18ms 左右完成, 不会有"偶尔特别慢"的情况。对于实时系统, **确定性比平均值更重要**——知道每帧必定在 18ms 内完成, 才能可靠地设计流水线。

### 6.3 SiLU 为什么检测全是 60 个框？

三帧都恰好是 60 个——这不是巧合。看 SiLU 的 `valid_candidates = 1084`, 而 `MAX_OBJ_BOXS = 60` (定义在 `post_process.h`)。它是**被硬上限截断的**。

实际上 SiLU 模型可能有远多于 60 个有效检测, 但代码只保留 NMS 后的前 60 个。这意味着:
1. SiLU 输出中高置信度的候选框非常多
2. 60 这个上限可能丢弃了部分有效检测
3. ReLU 的 18-24 个检出更接近真实目标数（1080p 安防画面通常就十几到二十几个目标）

### 6.4 模型大小为什么差不多？

| | SiLU | ReLU |
|---|---|---|
| ONNX 大小 | 27.6 MB | 28.9 MB |
| RKNN 大小 | 8.4 MB | 7.99 MB |

两个模型的**权重参数量完全相同**（都是 YOLOv5s 的 COCO 预训练权重）。ONNX 的微小差异来自激活函数节点在计算图中的编码方式。RKNN 转换后, ReLU 版略小是因为 ConvReLU 融合节点替代了 Conv + Sigmoid + Mul 三个节点, 图结构本身更紧凑。

这也说明:**激活函数的选择不影响模型的表达能力（参数量不变）, 只影响推理效率**。

### 6.5 收益归属

这个 A/B 实验的最大价值在于：**所有收益可以干净地归因**。

| 观察到的收益 | 归因 |
|---|---|
| 延迟从 45ms → 18ms (2.5x) | **ReLU 的算子融合**, 不是量化 |
| 延迟稳定性从 ±19ms → ±0.8ms | **DDR 流量减少 3x**, 消除了排队抖动 |
| 模型缩小 (28.9MB → 8.0MB) | **INT8 量化**, 与激活函数无关 |
| 尾延迟消除 (P99-P50: 30ms → 0.2ms) | **ReLU 的单指令执行**消除了 SiLU 的多步流水线停顿 |

**量化带来的体积缩减和融合带来的延迟加速是两个独立的优化杠杆**——这个实验把它们拆开了。

## 7. 综合结论

| 维度 | SiLU | ReLU | 胜出 |
|------|------|------|:---:|
| P50 延迟 | 45.2 ms | 17.8 ms | **ReLU 2.5x** |
| P95 延迟 | 64.6 ms | 18.0 ms | **ReLU 3.6x** |
| 延迟稳定性 | ±19ms | ±0.8ms | **ReLU 25x** |
| 模型大小 | 8.4 MB | 8.0 MB | 相近 |
| 端到端 FPS | — | 34.0 | — |
| 参数量 | 相同 | 相同 | — |

### 分维度结论

**推理速度**: ReLU 通过 Conv+ReLU 融合为单条 NPU 指令, 节省了约 2/3 的 DDR 带宽, 单帧推理加速 2.5-4.2x。

**延迟确定性**: ReLU 的 P95 仅比 P50 高 1%, 波动 1.5ms; SiLU 的 P95 比 P50 高 43%, 波动 38ms。在实时视频分析中, 确定性比平均值更重要——帧间隔是固定的 (33ms@30fps), 一次 65ms 的推理就意味着丢帧。

**精度影响**: 两者权重相同 (都是 COCO 预训练), 激活函数替换理论上有精度代价, 但需要标注数据做 mAP 评测才能量化。本实验未覆盖。

**量化 vs 融合**: 这是两个独立优化维度。INT8 量化负责模型压缩 (29MB→8MB), ReLU 融合负责推理加速 (45ms→18ms)。两者叠加才构成完整的"模型优化"故事。

### 收益归因

本次实验控制了架构、权重、校准集、量化策略、Toolkit 版本、板端 Runtime 全部变量。观察到的推理加速**纯粹来自 ReLU 替代 SiLU 后 NPU 算子融合**, 与量化策略无关。
